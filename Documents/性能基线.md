# 性能基线（3000 兵压测）

> 2026-11-07。这份文件只干一件事：**同一行参数、可复现地量**。
> 下结论前先跑一遍，别看截图猜。

---

## 1. 怎么跑

```powershell
$g = 'E:/Program Files (x86)/Steam/steamapps/common/Godot Engine/godot.windows.opt.tools.64.exe'
& $g --headless --path . --quit-after 240 -- --stress-units=3000 --perf-long=2
```

- `--stress-units=3000`：在**玩家基地外圈**螺旋铺 3000 个待命步兵
  （待命是最省的状态，测的是每帧固定开销）；
- `--perf-long=2`：每 2 秒打一行 `PERF2 {json}`；
- `--quit-after=240`：跑 240 帧就退（3000 兵时约 40~60 秒墙钟）。

**读哪几个数**（`sys` 里都是"每秒吃掉多少毫秒 CPU"）：

| 键 | 含义 |
|---|---|
| `unit` | 全部单位逻辑（分离/贴地/寻敌/移动） |
| `ai` | 所有 AI 大脑（`ai.ctx` / `ai.econ` / `ai.mil` / `ai.san` 是分项） |
| `fog` | 战争迷雾重算 |
| `hud` | 界面 |
| `proc_ms` | 每帧 `_process` 总耗时（毫秒） |

## 3. 这轮改了什么（为什么快）

### 3.1 AI：一个 tick 只扫一次全表

| 改动 | 位置 |
|---|---|
| `_snap_seq` 每 tick +1，下游按序号判断"算过没有" | `简单AI._think_once` |
| `_combat_units_of` 按「阵营 + 0.4s」**跨 AI 共享**缓存 | `简单AI._combat_units_of` |
| `_foe_census` 一次遍历产出 `by` + `ranked`，四个下游共用 | `简单AI._foe_census` |
| `_threat_units` 先过锚点 AABB，再算平方距离 | `简单AI._threat_units` |
| `_enemy_profile` 按「最强敌人 id + 0.6s 时间桶」缓存 | `简单AI._enemy_profile` |
| `army_value` 按 `def.id` 缓存单兵价值 | `战斗模型.army_value` |
| `ratio_with_profile`：画像由调用方给，不再内部重建 | `战斗模型.ratio_with_profile` |

**最容易踩的坑**：`array.hash()` 当缓存 key —— 它本身就是 O(3000)，等于又扫一遍。
用「阵营 id + 时间桶」。

### 3.2 迷雾：同格只点亮一次

`_mark_faction` 以前对**每个单位**点一个视野圆盘。3000 个挤在一起的步兵 =
3000 个几乎完全重合的圆（每个约 100 格），8Hz 重算 → 三百万次格子写入。

现在按 **4m 粗格**去重：同一格只保留半径最大的那个眼位点亮。
迷雾是"能不能看见"的近似，4m 偏差在画面上看不出来。

### 3.3 计时点

`性能探针.gd` 新增 `ai.ctx / ai.econ / ai.mil / ai.san / ai.mid / ai.flush`。
以后改 AI 先看这几个数，别猜。

## 5. 2026-11-14「A 段转正」：20Hz 移动卫生（同构建 A/B 实测）

玩家口径：「7~8 分钟单位变多就卡」。按 `Documents/万单位与SC2管线_可行性评估.md` §10
的 A 段（**换实现不换玩法**）先做"卫生部分"，**不动玩法数值**：

| 改动 | 位置 | 说明 |
|---|---|---|
| 分离 + 贴墙推出 → **20Hz** | `单位._tick_slow` / `SLOW_STEP=0.05` | 两者都是软纠偏，50ms 延迟看不出来 |
| 贴地目标高度 → **20Hz 采样**（站着 0.5s） | `单位._snap_ground` | y 仍每帧插值，画面不台阶；`height_at` 从 5 次/帧降到 5 次/20Hz |
| 空闲单位索敌 → **1s**（有指令仍 0.3s） | `单位._acquire` / `THINK_SLICE_IDLE` | 反应由 `take_damage` 立刻还手兜底 |
| 空闲待机动作快路径 | `单位._update_anim` | 已经站着 + idle 就整帧跳过动画推送 |
| 分离位移上限 0.35m/tick | `SEP_MAX_STEP` | 20Hz 步长变大也不许一把推穿墙 |

### 5.1 怎么复现（同构建切开关）

```text
# A：新口径（20Hz 门开）
godot --headless --fixed-fps 60 --path . --quit-after 1200 -- --stress-units=600 --perf-long=2
# B：旧口径（每帧分离，门关）
godot --headless --fixed-fps 60 --path . --quit-after 1200 -- --stress-units=600 --perf-long=2 --legacy-move
```

### 5.2 结果（600 兵待命，`--fixed-fps 60`，中位数 9 个采样）

| 项（ms/秒） | 旧口径（每帧） | 新口径（20Hz 门） | 变化 |
|---|---:|---:|---:|
| `u.sep` 分离+推出 | 1115 | **383** | **-66%** |
| `u.ground` 贴地+动画 | 242 | **143** | **-41%** |
| `unit` 全部单位逻辑 | 1951 | **1095** | **-44%** |
| `u.order` / `o.acq` | 172 / 37 | 167 / 38 | 持平（这两项由索敌周期决定） |
| 实测 fps | 18~21 | **23~28** | +25~30% |

### 5.3 3000 兵压测为什么看不出分离收益（别拿它下结论）

`--stress-units=3000` 在无头下只有 **2 fps**，`delta ≈ 0.4s`：
20Hz 门每次累加都比 `SLOW_STEP` 大，于是**每帧都会开**（等价旧口径）。
这不是 bug —— 20Hz 门的作用是"帧率够高时别每帧都算"，帧率本身已经掉到 2 fps 时它自然退化。
所以：

- 判断 20Hz 收益 → 用 **600 兵 + `--fixed-fps 60`**；
- 判断"单位多了以后还卡不卡" → 用真机长局看右上角 FPS（HUD 常驻，2026-11-14 起）。

3000 兵（2 fps）同口径对比：`unit` 2150 → 1571（-27%）、`proc_ms` 950 → 659，
收益来自空闲索敌降频（`o.acq` 560 → 136）与贴地/动画快路径 —— 这两项与帧率无关。

## 6. 2026-11-14 真正的"越打越卡"元凶：**每帧强制重算路径**

做完 20Hz 卫生之后，10 分钟长局（`--perf-long=15`）里抓到了真正的悬崖：

| 时刻 | 单位数 | fps | `proc_ms` | `o.goto` | `path_n`（A*/秒） |
|---|---:|---:|---:|---:|---:|
| t=45s（修前） | 82 | **18** | 91 | 2316 | **4208** |
| t=45s（修后） | 82 | **141** | 41 | 27 | **119** |
| t=7.5min（修后） | 165 | 55 | 55（偶发 200+） | 100 | 380 |

根因：`_order_attack` / `_order_attack_move` / `_update_attack` 的"继续走完目标"分支
**每帧**调 `_go_to(..., force=true)`。`force` 会把 `_repath_cd` 清零（本来是 0.25s 节流），
于是每个有指令的单位每帧都跑一次完整 A*（104µs）—— 几十个单位围一个目标就是每秒几千次。

修法：这三处去掉 `force`（目标没变，交给 `_request_path` 的 0.25s 节流 + 每帧配额）。
副作用只有"最多晚 0.25s 顶上去"，`--autotest`、`战斗自检`、`寻路自检` 全过。

**还剩下的**：偶发单帧 200~300ms 尖峰（`proc_ms` 最大 325），
`unit`/`ai` 的每秒累计都只有几百 ms，说明是**一次性操作**（建楼生成网格 / 部署判定之类），
不是持续开销；下一步要定位它得在 `Performance.TIME_PROCESS` 尖峰那帧打调用栈。
