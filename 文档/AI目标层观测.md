# AI 目标层：达成率口径 / 次目标补选 / 空过收敛（2026-11-07）

> 三个改动都在 `代码/ai/简单AI.gd`；**阈值 0.6 一个字没动**
> （`代码/ai/目标层.gd:77 URGENCY_THRESHOLD_DEFAULT` 仍是唯一真值）。

## 1. 达成率：改成 AI-only，且是纯观测

### 问题
旧口径（外部 `analyze_2c13.py`）的分子来自 `wave_records`，而 `_collect_brains()`
**同时收了 `ai_brain` 和 `adjutant`** —— 副官指挥的是玩家阵营，所以"达成率"一直是
AI + 玩家混合口径。玩家手操打出来的达成也被算进 AI 头上。

### 现在（不参与决策）
`dept_stats` 新增四个计数，`_goal_tick` 的"目标释放"循环里累加：

| 键 | 含义 |
|---|---|
| `goal_metric_total` | **AI 阵营**的目标结束次数（达成+过期+被抢占） |
| `goal_metric_done` | 其中"达成"的次数（原判定） |
| `goal_metric_strict_done` | 其中"按期望值也算达成"的次数 |
| `goal_ai_created` | AI 阵营创建过多少目标 |

- 只统计 `_faction.is_ai == true`；副官的计数恒 0（不算进分母）。
- `_goal_strict_ok()`：训练/建造要求 `当前数量 − 开目标时基数 >= 期望值`，
  不是"多 1 个就算达成"；区域/到达/威胁三类无法回溯开目标时状态，沿用原判定。
- 落到 bench：`monitor_2c13` 里的 `目标结束(AI-only)` / `达成事件(AI-only)` /
  `达成率(AI-only)` / `达成率(AI-only,按期望值)`。
- 落到 L3 日志：`AI达成率` / `AI目标结束数`。

**这些数字一个都没进 `_goal_execute` / 仲裁 / 预算。** 改坏了只会让报告变难看。

## 2. 次目标补选（降低空置）

### 问题
`_goal_select` 在"主目标还活着"时直接 `return`，次目标只有"新选主目标"那一刻
才顺带选一次。次目标一旦结束（晋升/达成/过期）就永久为空 —— 实测空置率 89%。

### 现在
- 主目标存活时，每个 2s 周期都调用 `_goal_fill_sub(props, now)` 尝试补位；
- 候选必须 `紧迫度 >= _goal_thr`（仍是 0.6）；
- 与主目标、与任何活动目标**同「动作|对象」**的跳过（不靠 id，
  因为提案 id 每周期重编号，直接用会撞掉正在执行的目标）；
- 冷却中的跳过；
- 落地 id 加 `Sub_` 前缀，保证不和 `goals_active` 里已有的 id 冲突。

实测（3 分钟、seed 7）：次目标为空占比 **89% → 35.2%**，补选 18 次。

## 3. 空过收敛（减少 3 秒内进出）

### 3.1 冷却
- `GOAL_COOLDOWN_SEC = 4.0`：目标结束时按「动作|对象」记 `now + 4s`；
- `_goal_select` 选主/次前先把冷却中的候选过滤掉（`goal_cd_skips` 计数）；
- **全被过滤 → 仍然走空过**，不硬塞目标、不降阈值。

### 3.2 空过期间不许花钱（补漏）
原来只有仲裁分支受 `goal_noop` 约束，`反愚蠢.update()` 是旁路：
`_check_supply`（建农场）/ `_check_production`（训练）/ `_check_gold_float`（研究/训练）
会在空过期间继续开新开销。

现在 `ctx["goal_noop"]` 传进审计，这三项整块跳过；
派工/接续/救场（不花钱）照跑。`_site_recovery_tick` 只接续**已付款**的工地，不受影响。

## 5. 抢占判定也按「动作|对象」（2026-11-08）

`_goal_best_new()` 决定"这一周期谁有资格抢正在执行的目标"。老条件只按 id 排
（`goals_active.has(pid)` / `has("Sub_"+pid)`）—— 但提案 id 是**每周期按本线第几条重编**的：
前面那条提案一消失（农场一开工就不再报建造、兵营一到位就不再报扩建），后面所有人的序号
整体前移。于是"同一个 动作|对象 的原提案"下一周期换了 id，排不掉它自己 → 被当成全新建议
→ 抢占 → 目标结束 → 该 动作|对象 进 4 秒冷却 → 这 4 秒里主/次都选不回来（玩家说的"4 秒空窗"）。

现在**按 id 和按「动作|对象」各排一次**（`_goal_key()`）：同一条活干着的时候，它自己的
提案永远抢不掉自己，不管 id 怎么漂。§2 次目标补选用的也是同一把尺子（那里已写明"不靠 id"）。

> 代价：活着的目标**不会**被"同一件事、但紧迫度更高"的提案原地刷新 —— 这是有意的：
> 同一条活抢自己只会产生"结束 → 4 秒冷却 → 再选回来"的空转，不会让它做得更快。

实测（10 分钟、seed 1、`--ai-bench`；**三局代码不同，对局会分叉，只看量级不看单值**）：

| 键 | 改前（a197adf） | 只按 id | id + 动作\|对象 |
|---|---|---|---|
| `次目标为空占比` | 0.537 | 0.520 | **0.466** |
| `释放_被抢占` | 5 | 8 | 5 |
| `空过周期占比` | 0.192 | 0.138 | 0.141 |

`配置回归` 仍只红那两条已知项（`DEPT_MODE` 默认 on 的旧断言），与本轮无关。
