# 人群层：一万个单位，零个节点

> 状态：现行（2026-11-13 落地并实测）
> 代码：`代码/人群/` · 场景：`场景/人群演示.tscn` · 模块说明：`代码/人群/README.md`
> 前情：`文档/万单位与SC2管线_可行性评估.md`（选型）、`文档/寻路评估_星际2对照.md`（算法对照）

---

## 0. 一句话

> 现有节点制单位（`单位.gd`，3754 行）**一行没改**；人群层是一条独立管线：
> 位置/速度/血量全在 `Packed*Array` 里，逻辑固定 20Hz，渲染走 MultiMesh，
> 1000 单位 1080p 实测 **546 fps**，10000 单位 **71 fps**。

---

## 1. 为什么另起一层，而不是改 `单位.gd`

| 维度 | 节点制（主线） | 数据导向（人群层） |
|---|---|---|
| 一个单位 | 1 个 `Node3D` + 10 个子节点 | 12 个数组里的一个下标 |
| 逻辑频率 | 跟渲染帧（60Hz） | 固定 20Hz |
| 动画 | `AnimationPlayer`（骨骼/逐单位） | 顶点着色器程序动画（相位错开） |
| 适用规模 | 20–60（含技能/举盾/建造） | 1k–10k（只有移动/推挤/集群观感） |

主线要保留举盾、建造、采集、技能前后摇 —— 这些**MultiMesh 给不了**。
所以按评估文档走"双轨"：主线不动，人群层独立验证技术，将来按需回灌。

## 2. 四个关键技术点（都有实测支撑）

### 2.1 位运算索引：热循环里没有一个 `int /` 或 `int %`

实测（Godot 4.7.2，20 核，固定 400 万次迭代）：

| 运算 | 1 线程 | 8 线程 | 结论 |
|---|---:|---:|---|
| `int /` | 84.5 ms | 173.6 ms | **0.49×，越开越慢** |
| `int %` | 84.4 ms | 175.7 ms | **0.48×** |
| `>>` + `&` | 72.2 ms | 13.0 ms | 5.53× |
| 浮点乘 | 73.4 ms | 12.4 ms | 5.91× |

落地：1m 寻路格 256²（`(z<<8)|x`）、4m 空间桶 64²（`((z>>2)<<6)|(x>>2)`）、
2m 流场 128²。所有索引 = `floori(w)+128` 后移位。

### 2.2 空间分区：计数排序的平坦网格

`人群空间.gd`：先数每桶几个人 → 前缀和 → 把下标填进连续 `PackedInt32Array`。
零 `Dictionary`、零 `Variant`、零每帧分配；最挤的桶 30–190 人，查询 3×3 桶。

### 2.3 流场：桶队列 + 方向平滑 + 双线性

- 2m 格（16384），桶队列 Dijkstra（代价量化 0.1m，直 10 / 斜 14），单次 **24 ms**；
- 方向场做 3×3 加权平滑（中心 4 / 边 2 / 角 1），消掉 8 方向折线；
- 采样时双线性插值，单位不在格心也不会有 2m 台阶；
- 每 2s 兜底重建，且**每 tick 最多建一个**（4 个军团同时到期会造成 100ms 尖峰）。

### 2.4 渲染：一次写 buffer + 顶点着色器动画

`MultiMesh.buffer` 布局（`_qa/mm_probe.gd` 实测）：12 个 float / 实例，
`[0..2]=basis 第 0 行, [3]=origin.x, [4..6]=第 1 行, [7]=origin.y, [8..10]=第 2 行, [11]=origin.z`，
开 `use_custom_data` 后再跟 4 个 float。

- 位置插值：CPU 每帧 `prev + (cur-prev)*alpha`（逻辑 20Hz → 画面 60fps）；
- 姿态动画：`INSTANCE_CUSTOM.x` = 相位（`i * 0.618` 黄金比散列），
  腿摆 / 躯干反摆 / 呼吸全在 `人群单位.gdshader` 里按 `TIME` 连续计算 —— **不受 20Hz 限制**。

## 3. 行为层：看路 / 互让 / 推挤

| 规则 | 实现 | 参数 |
|---|---|---|
| 看路 | 正前方 `LOOK_AHEAD=2.2 + 2r` 探一次；受阻才在 ±80° 按 7 档扫，取最接近原方向的**连续可走**角 | 7 档 |
| 互让 | 迎面接近（`closing>0.6` 且 `d<1.6`）时读对方 `side` 字节：已定的一侧说了算，都没定按 `(i^j)` 奇偶定死；只加横向分量 | 保持 0.35s |
| 推挤 | 份额 = 我的可推程度 / 双方之和；空闲 1.0、行军 0.8、驻守 0.15；快者再乘 `clamp(1-v/(v+v')*1.6, 0.25, 0.85)` | 每 tick 上限 1.8m/s |
| 空中 | `ST_AIR` 不参与推挤、不吃流场，直奔 `goal+slot` 并悬停 | 阵型靠 slot |
| 邻居预算 | 最挤的桶会到 190 人，全查是浪费；每单位最多查 16 个 | 16 |

**方向 pass 独立**：`_update_dirs()` 每 4 个 tick 跑一次（流场采样 + 看路），
steer 只做推挤 + 乘法。这一步让 4000 单位的 steer 从 **85 ms 降到 2.4 ms**。

## 4. 实测（RTX 5060，1080p，关垂直同步）

| 单位数 | FPS 均值 | tick 均值 | steer | spatial | flow | draw | draw calls |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1,000 | **546** | 4.6 ms | 1.3 | 0.27 | 1.8 | 0.8 | 20 |
| 2,000 | 480 | 6.4 ms | 1.7 | 0.42 | 1.9 | 1.5 | 20 |
| 4,000 | 350 | 9.9 ms | 2.4 | 0.68 | 2.0 | 2.8 | 20 |
| 10,000 | **71** | 20.0 ms | 4.9 | 1.45 | 1.8 | 6.6 | 20 |

- 逻辑预算：20Hz → 每 tick 50ms。10,000 单位 tick 20ms，**占用 40%**。
- 渲染：10000 个实例仍是 20 个 draw call（MultiMesh 1 个 + 箭 1 个 + 场景 18）。

复现：

```text
godot --path . --resolution 1920x1080 res://场景/人群演示.tscn -- --crowd-bench=1000 --crowd-secs=8
godot --path . --resolution 1920x1080 res://场景/人群演示.tscn -- --crowd-bench=10000 --crowd-secs=8 --crowd-shot=_qa/crowd/10k.png
```

## 5. 踩过的坑（每条都花过一次调试）

| 现象 | 根因 | 修法 |
|---|---|---|
| 进程卡死、无输出 | 流场桶队列用 `Array[PackedInt32Array]`，取出后 `pop_back` 改的是 CoW 副本 | 换普通 `Array`（引用语义） |
| 同上，第二次 | 用 `head+next` 链表，同一格重复入桶覆盖 `_next` 导致成环 | 同上 |
| 10000 单位 tick 101ms、线程池没加速 | `chunks = n/512` 整数除，1000→1 块 | 向上取整 + 每块 ≥512 |
| 后排方阵原地列队 | `assign_group` 只写 slot 没写 `goal` | 补 `goal_x/goal_z` |
| 队伍被压成一条纵队 | 阵型权重 `k = 1-gd/50`，远处归零 | 给一个 0.45 的底 |
| 单位像"倾斜的板砖" | BoxMesh 一整块 + 全身摆动 | 换胶囊体 + 腿段单独摆 |
| headless 下 `MultiMesh.buffer` 长度 0 | dummy 渲染器不存实例缓冲 | 压测必须真实渲染 |

## 6. 与主线的关系（下一步可选项）

| 可回灌项 | 收益 | 风险 |
|---|---|---|
| 拐角圆角（`人群导航.fillet`） | 主线拐角不再贴墙减速 | 低（纯后处理） |
| 推挤规则（`push_weight` 分配） | 12 人不再"整队左右扭" | 中（要改 `单位.gd` 分离） |
| 相位错开动画 | 100 个兵待机不再齐步走 | **极低**（1 行） |
| GPU 箭矢 | 省节点 + 修 `_t` 过冲 | 中（要拆 `投射物.gd`） |

**不建议**：把 `单位.gd` 全量改成 SoA —— 会丢举盾/技能前后摇/逐单位动画，
而玩法只需要 20–60 个单位（见评估文档 §6 路线 C）。
