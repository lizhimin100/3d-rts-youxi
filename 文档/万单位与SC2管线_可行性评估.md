# 万单位与 SC2 管线：可行性评估与选型

> 只读排查 + 本机实测。未改动游戏代码（基准脚本在 `_qa/`，已被 gitignore）。  
> 结论按"能不能做 / 值不值得做"分开说——这两件事在这个工程里经常不是一回事。

## 1. 先算账：10k 到底差多少

### 1.1 现状（`文档/性能基线.md`，3000 待命步兵，headless）

| 项         |               数值 | 含义                                                       |
| --------- | ---------------: | -------------------------------------------------------- |
| `proc_ms` | **352–411 ms/帧** | 3000 兵时每帧光 `_process` 就要 0.35–0.41 秒 → 约 **2.5–2.8 fps** |
| `unit`    |   1150–1200 ms/s | 单位逻辑合计                                                   |
| `u.sep`   | **583–705 ms/s** | 最大单项，占单位逻辑一半                                             |
| `fog`     |       56–65 ms/s | 4m 去重后的迷雾                                                |
| `ai`      |      40–120 ms/s | 7 个 AI 大脑                                                |
| `hud`     |     8.6–9.8 ms/s | 界面                                                       |

> 注意：这是 **headless**，一个模型都没画。渲染预算是空白。

### 1.2 外推（估算，标注清楚）

- 3000 → 10000 = **3.33×**。按 O(n) 主导外推：`proc_ms ≈ 1170–1370 ms/帧`。
- 60fps 预算是 **16.67 ms/帧** → 需要 **70–82 倍**的降幅。
- 即便只要求 3000 兵 60fps，也需要 **21–25 倍**。

这个量级不是"把循环写紧一点"能到的，必须换执行模型。

### 1.3 渲染预算（按现状外推）

| 项                   |           单兵 |          1 万 | 备注                    |
| ------------------- | -----------: | -----------: | --------------------- |
| 场景节点                |    11（带盾 12） |    **≈11 万** | 每节点都有 `_process`/变换更新 |
| SkinnedMesh surface |            3 |      **3 万** | MultiMesh 不支持蒙皮       |
| draw call           | 4（3 蒙皮 + 阴影） |      **4 万** | 必须靠 MultiMesh 压到 3–4  |
| 顶点                  |         7176 | **7176 万/帧** | 60fps 不可能，必须先做远距 LOD  |

结论：**渲染和逻辑都要换模型**，而且逻辑先崩（3000 兵已 2.5 fps，此时一个模型都没画）。

## 2. 实测：多线程里整数除法到底行不行

你的说法我做了基准验证（Godot 4.7.2 stable mono，20 核，`_qa/bench_int2.gd`）。  
**固定总工作量 4,000,000 次迭代**，只改线程数，数字是相对 1 线程的加速比：

| 运算           |     1 线程 |                2 线程 |                4 线程 |                8 线程 | 结论        |
| ------------ | -------: | ------------------: | ------------------: | ------------------: | --------- |
| `a / b`（整数）  |  84.5 ms | 141.6 ms（**0.60×**） | 135.9 ms（**0.62×**） | 173.6 ms（**0.49×**） | **负加速**   |
| `a % b`（整数）  |  84.4 ms | 147.5 ms（**0.57×**） | 161.5 ms（**0.52×**） | 175.7 ms（**0.48×**） | **负加速**   |
| `/` 与 `%` 同时 | 126.5 ms | 247.1 ms（**0.51×**） | 254.0 ms（**0.50×**） | 252.1 ms（**0.50×**） | **稳定慢一倍** |
| `>>` 与 `&`   |  72.2 ms |      36.6 ms（1.97×） |      18.4 ms（3.92×） |      13.0 ms（5.53×） | 近线性       |
| 浮点乘          |  73.4 ms |      37.8 ms（1.94×） |      18.5 ms（3.97×） |      12.4 ms（5.91×） | 近线性       |

另有一组"每线程做满额工作量"的测试：`/` 2 线程墙钟 270.7 ms，单线程 64.2 ms —— 单位工作量的耗时变成 **2.1 倍**；而 `>>` 2 线程 40.8 ms ≈ 单线程 41.0 ms，**吞吐正好翻倍**。

### 2.1 怎么解读

- **整数除余在多线程下不只是"不提速"，而是慢一倍**，且线程越多墙钟越长。最可能是这条路径上有共享状态/锁（具体在引擎哪一层不重要，现象可复现）。
- **位运算与浮点能线性扩展**（8 线程 5.5–5.9×，受超线程和内存带宽限制）。
- 所以"线程池分块算"**本身没错**，错的是把含 `int /`、`int %` 的循环丢进去。很多"越优化越慢"的案例，就是循环里藏了一个 `% n`。

### 2.2 直接落成架构规矩

1. 热循环里禁止 `a / b`、`a % b`（整数）。需要索引就换成位运算。
2. 网格尺寸取 **2 的幂**：地图边长 224 → 内部按 **256** 铺；空间分区 4m 桶 → `idx = (z >> 2) * 64 + (x >> 2)`。
3. 负坐标不用担心：GDScript 的 `>>` 是算术右移（向下取整），`-1 >> 4 == -1`、`-1 & 15 == 15`，正好是我们要的格。
4. 环形缓冲不要 `i % n`，用 `if (++i >= n) i = 0`。
5. 线程池只在"纯浮点/位运算 + 大块数据"上用；块小于 ~500 个单位时，调度开销大于收益。

### 2.3 分离内循环代理（单线程 GDScript）

n 个单位、每个查 20 个邻居的距离平方（含一次 `%`，所以是**悲观值**）：

|      n | ms/tick | 20Hz 占 50ms 预算 |
| -----: | ------: | -------------: |
|  1,000 |    1.10 |           2.2% |
|  3,000 |    3.29 |           6.6% |
| 10,000 |   11.12 |          22.2% |

对照现状：3000 兵 `u.sep` 583–705 ms/s ≈ **9.7–11.8 ms/帧**（60fps）。  
也就是说，**"数组化 + 20Hz"这两件事就能把分离从 ~10ms/帧 降到 ~3.3ms/tick**，约 **9–10 倍**——比换算法便宜得多。

## 3. SC2 四步：逐项可行性

### 3.1 jump & walk 点定位 —— 不需要

它的存在是因为三角形大小形状不一，坐标除法无法定位。我们的图是 1m 方格，`world_to_cell` 一次除法就够（`网格寻路.gd:174`）。**除非上 CDT，否则这条没有对应物。**

### 3.2 三角形 A* —— 不做

前置是 CDT 导航网格。我们的 A* 单次 0.4–2.3 ms、每帧上限 6 条，约占 1.4% CPU；瓶颈不在这里。详细论证见 `寻路评估_星际2对照.md` §3.A。

### 3.3 只记接下来两个拐点 —— 可以做，但优先级低

SC2 这么做是因为"世界随时在变，一次算到终点是白算"。我们的等价物是"整条路径 + 0.25s 节流重算"。  
可借鉴的形式不是"只存两个点"，而是 **路径窗口**：

- 仍然算全程，但单位只消费前 2–3 个拐点；
- 偏离折线 > 0.8m 或窗口耗尽时，从当前位置重算；
- 好处：动态障碍反应更快、每单位路径内存从 20–40 个点降到 3 个。

代价 1 天。**建议放到 20Hz 改造时一起做**，因为那时每 tick 的路径内存和重算次数才成为问题。

### 3.4 半径膨胀过角 —— 做，两档实现

我们现在已经有：净空表 `_clear`（`网格寻路.gd:314`）、带半径的 LOS、贪心拉直（`668-714`）、`GOAL_MARGIN=0.15`。  
缺的是"拐角不是一个格心，而是一段圆弧"。两档：

| 档              | 做法                                                                      | 工作量   | 风险 | 适用               |
| -------------- | ----------------------------------------------------------------------- | ----- | -- | ---------------- |
| **A 圆角（推荐先做）** | 拉直后的折线上，每个拐点用半径 `r = body_radius + 0.12` 的圆弧替换；弧采样 2–4 点；用现有 LOS 校验弧不穿墙 | 3 天   | 低  | 现在就能上            |
| B 圆-切线（视频原版）   | 以阻挡格顶点为圆心画圆，从上一拐点求切线，两角之间走公切线                                           | 5–7 天 | 中  | 只有上了 20Hz/人群层才值得 |

**一条不能照抄的**：视频说"碰撞体积严丝合缝贴墙而过，不会卡住减速"。我们的分离每帧最多推 0.027m，零余量落点被推 1mm 就掉出 `is_standable`，然后 `wall_pushout` 推回来，每帧对拉——`网格寻路.gd:45-52` 的注释记的就是这个事故。**圆角可以抄，"零余量"不能抄。**

## 4. 行为层四件事

### 4.1 看路（能，2 天）

现状：`_steer`（`单位.gd:3622`）先测正前方，受阻再试 2 方向 × 4 个固定偏角（20/40/60/80°），每个候选做 3 次查询。  
视频的做法更进一步：**先把前方障碍的"空隙"扫出来，瞄准空隙中心**，而不是试固定角度。

改法：把 8 个候选角换成"在 ±80° 弧上按 5° 采样一次可走性，找连续可走段（空隙），取段中心"。成本相近，但走位更自然，尤其过 2m 缝。**不改 A*，只改这一个函数。**

### 4.2 互让（能，1 天）

现状：`_slide_side` 是**每个单位自己的方向记忆**，靠它避免左右横跳（`单位.gd:3653`）。  
视频的做法是**读对方的意图**：他已经决定往左躲，我也往左，两人就错开。

改法：给每个移动单位一个 `side_intent`（-1/0/+1，1 字节），保持 0.3s；邻居在做避让决策时先读对方的值，双方都未决定时按 `unit_id` 奇偶定侧（确定性平局）。  
成本：一个字段 + 两处判断。收益：走廊迎面不再"跳舞"。

### 4.3 推挤（能，2 天）

现状：`_unit_ahead` **只避让停着的同伴**（`单位.gd:3690`）；`_update_separation` 对所有人生效，干活方权重 0.13（`单位.gd:2766`）；没有"谁更容易被推"。

视频规则 → 我们的字段：

| 视频规则        | 我们的实现                                                                |
| ----------- | -------------------------------------------------------------------- |
| 空闲/待命可推     | `push_weight = 1.0`（现状已近似）                                           |
| 同方向行军可推     | 点积 > 0.6 时 `push_weight *= 1.3`                                      |
| 快者少被推、慢者多被推 | `share = 1 - clamp(speed_self / (speed_self+speed_other), 0.2, 0.8)` |
| 干活的一方少被推    | 已有 `_anchor_weight` 0.13，保留                                          |
| Hold 抗推     | `order == HOLD` 时 `push_weight *= 0.15`，但仍允许被"硬挤"开一点、且不回位            |
| 对敌军双方对推     | 敌方时 `push_weight` 取双方均值                                              |

成本：一个 `push_weight()` + 改 `share` 的算法。**这是"手感"最便宜的一次升级。**

### 4.4 空中无碰撞但保持阵型 —— N/A

已核实：`UnitDef` 没有 `flying`/`is_air` 字段，`代码/配置/卡/单位/` 只有 7 张卡、全是地面单位。  
"到点先聚拢再散开"对地面编队仍可用：`_spread_goal`（`单位.gd:2339`）已有环形候选，但环上只能放 8 个位置（周长 7.85m ÷ 间距 0.906m）。把容量按 `floor(2πr / spacing)` 算、不够加一圈即可（见 `寻路评估` P1-3）。

## 5. 万单位：八个技术点逐个判断

### 5.1 MultiMesh + 不建引擎节点

**必须做，且是唯一解。** 现状 11 节点/单位、3 个 SkinnedMesh、4 个 draw call；1 万 = 11 万节点、3 万 surface、4 万 draw call。  
MultiMesh 化后：3–4 个 draw call、0 个节点。

**但**：MultiMesh 不支持蒙皮、不支持逐实例 `AnimationPlayer`、不支持 `material_overlay` 闪白、不支持逐实例 Tween。  
所以它不是"给现有单位换个画法"，而是**另一套实体**：只有位置/朝向/血量/一个动画相位，没有举盾、没有攻击前后摇的独立骨骼、没有受击顿挫。

### 5.2 SoA + 线程池

**SoA 必须做**（数组化后分离快 3 倍，见 §2.3）。线程池要分情况：

- 纯浮点/位运算：可以，实测 4 线程 3.9×。
- 含整数除余：**不要**，实测 0.5×（越开越慢）。
- GDScript 的每次跨线程调用有开销，块要 ≥500 单位；用 `WorkerThreadPool.add_group_task` 而不是裸 `Thread`。

### 5.3 均匀网格 + 位运算

**做。** 现状 `SpatialHash` 是 `Dictionary` + 数组（`寻路/空间哈希.gd`），每次查询分配、每次插入 boxed Variant。  
改成"计数排序"式平坦网格：每 tick 先数每格数量 → 前缀和 → 填索引数组。查询零分配。  
配合 §2.2 的位运算，索引一次 `>>`/`&` 搞定。**这条对 3000 兵也有直接收益，不需要等万单位。**

### 5.4 流场 + 方向平滑

流场只在"同一目标 + 数量 ≥30–50"时划算（一次 Dijkstra 铺 50k 格 ≈ 25–50ms，我们一条 A* ≈1ms）。  
你要的"多做一步平滑修正"是必须的：1m 格 + 8 方向，原始流场只有 8 个方向，单位会走 45° 折线。平滑做法：对方向场做 3×3 均值 + 用积分场双线性梯度替代离散邻居选择。  
结论：**做成"军团模式"的可选路径**，不要替代 A*。

### 5.5 逻辑/渲染彻底拆开

目标态正确，但现状是"逻辑对象 = 渲染节点"：

- 单位根 `Node3D` 同时是逻辑坐标、渲染父节点、外部查询源；
- 至少 8 处表现层每帧读 `unit.global_position`（血条/选中圈/攻击圈/指示线/小地图/LOD/受击方向）；
- `visual.position` 已经被采矿下沉动画占用（`单位.gd:3555`），不能直接拿来当插值偏移。

所以拆分 = 新增"模拟坐标 + 渲染代理 + 插值层"，并改 8 处读取点。**约 12 个文件**，不是 3 个。

### 5.6 逻辑 20Hz

**收益最大，但牵动最广**：26 个运行时 `_process`、≥110 处按 dt 积分、6 处直接改 `Engine.time_scale`。

必须先修的三个坑：

1. `Game.unit_hash()` 的缓存键是 `Engine.get_process_frames()`（`游戏状态.gd:384`）。一帧跑多个 tick 时，第二个 tick 会读到上一 tick 的哈希（位置已变）→ **直接算错分离/索敌**。改成 tick 号。
2. `单位.gd:1481` 把 dt 夹到 0.1，并注记"`time_scale=5` 时只跑 60%"。固定步长后要换成"单帧最多补 N 个 tick"，否则 `建造自检` 的 `time_scale=20` 会雪崩。
3. 输入延迟：指令写入是即时的，但单位反应要等下一个 tick（平均 25ms、最大 50ms）。点地到起步会"迟钝"。解决：写指令时立刻推一次该单位的最小 tick。

### 5.7 顶点着色器动画（VAT）

要分清两件事：

- **程序化摆动**（呼吸/上下颠/前倾）→ 纯 shader 可做，成本低。
- **骨骼动画**（我们的模型 24–37 骨、5–11 个 clip）→ **必须 VAT**：把每帧每骨变换烘到一张纹理，顶点着色器按时间采样两帧并插值。这是人群渲染的标准做法，Godot 没有现成组件，要自己写烘焙工具 + 着色器。

"插值补帧"这句话要拆开：逻辑 20Hz 需要插值的是**位置/朝向**；动画本身应按渲染时间独立推进（60fps），不需要在 20Hz 姿态之间插值。  
"错开节拍"：`phase = hash(instance_id) * cycle`，放进 `INSTANCE_CUSTOM.x`，**一小时就能做，主线也能用**。

### 5.8 箭矢只记命中时间

现状其实已经很接近：`投射物` 没有碰撞检测，命中判据是 `k >= 1`（`投射物.gd:137`），落点结算。

但**不能"只记时间"**，必须记一条排队记录：`命中时间 + 目标引用 + 出手伤害快照 + 终点 + AOE 参数 + 减速参数`。原因：

- 落点要读**存活目标**的护甲/格挡/受伤倍率（`战斗.gd:402-420`）；
- AOE 中心点是落点时刻的位置（`投射物.gd:279`）；
- 目标中途死了要哑火但仍播特效（`投射物.gd:301`）；
- 命中音效/震屏是落点时刻的相机位置（`战斗.gd:517`）。

GPU 只负责画抛物线：`from/to/t0/dur` 四个量进 `INSTANCE_CUSTOM`，顶点着色器算位置。**顺带修一个现存 bug**：`投射物.gd:130` 用未 clamp 的 `_t` 算 y，最后一帧会过冲（60Hz 约 4cm，20Hz 约 12cm，`time_scale=5` 时约 30cm）。

## 6. 三条路线

| 路线           | 内容                                             | 工作量    | 结果                                | 风险          |
| ------------ | ---------------------------------------------- | ------ | --------------------------------- | ----------- |
| **A 性能卫生**   | SoA 分离、位运算网格、UI 上限、死常量、错开节拍                    | 1–2 周  | 3000 兵从 ~2.7fps → **8–12fps（估算）** | 低           |
| **B 双轨（推荐）** | A + 独立"人群层"（MultiMesh + VAT + 20Hz + 流场），主战线不动 | 4–6 周  | 万单位演示 60fps；主游戏手感不变               | 中（新模块，可随时砍） |
| **C 全量重写**   | 把 3754 行单位类改成 SoA 实体                           | 3–6 个月 | 10k 可跑，但丢举盾/逐单位动画/技能表现            | 极高          |

**推荐 B。** 理由：

1. 这个游戏的玩法是 20–60 个单位 + 建筑 + 技能，10k 是技术演示，不是玩法需求。为演示重写主线不划算。
2. 万单位的每一块技术（MultiMesh、VAT、20Hz、流场、命中队列）都可以在"人群层"里独立验证，验证完再决定要不要回灌主线。
3. 主线的性能问题（分离、UI 上限、位运算）在 A 里就能拿到 3–4 倍，**不需要等万单位**。

## 10. 2026-11-13 实测更新：VAT 做完了，转正条件可以量化了

`工具/烘焙VAT.gd` + `代码/人群/人群VAT.gd/.gdshader` 已经落地：真模型（联盟步兵）的
idle / walk 烘成 RGBAH 纹理，MultiMesh 顶点着色器按帧采样 + 每实例黄金比相位错开。
和本文 §5.7 当初的估计相比，有四个**实测修正**：

| 项 | 当初的判断 | 实测 |
|---|---|---|
| VAT 采样成本 | "骨骼矩阵 VAT，每顶点 24 次采样" | 改成**顶点位置 VAT** 后每顶点 8 次（两帧 × 位置/法线） |
| 纹理大小 | 未估 | 7336 顶点 × 108 帧(idle) ≈ **12MB/单位/clip**；10fps 烘只要 4MB |
| 帧时间代价 | 未估 | 胶囊 vs VAT：1k → 820/483 fps、5k → 198/127、10k → 78/53（**1.5~1.7×**） |
| draw call | 预计 +3~9 | 反而 **−5**（3 个 surface 合并成 1 个） |

**两个坑（都会让结论错得离谱）**：

1. `MultiMesh.visible_instance_count` 不设 = 把**容量**（10000）个实例全跑一遍顶点着色器，
   缩放 0 的也照跑。实测 100 兵和 1000 兵都是 55fps，设成实际数量后 1000 兵 483fps。
   任何用 MultiMesh 做压测的地方都要先检查这一行。
2. 人群模拟的 `yaw` 是 **+Z 约定**（`atan2(vx,vz)`），而模型正面是 **-Z**（骨骼静止坐标
   实测：盾/武器骨 z 全为负，与主线 `atan2(-dx,-dz)` 一致）。胶囊体看不出来，
   换真模型就是"整队背朝行进方向"。渲染层补 `π`，**不要改模拟层的 yaw**。

### 什么时候把"新移动板块"转正（拍板用）

先分清两件事：**执行模型**（SoA/20Hz/MultiMesh）和**玩法**（攻击前摇、技能、采集、建造、选中、血条）。
人群层现在只有前者，玩法一件都没有；节点制反过来。所以"转正"不是替换，是分三段：

| 段 | 内容 | 触发条件（可量化） | 现在的值 |
|---|---|---|---|
| A | **20Hz + SoA 分离/空间网格回灌节点单位**（换实现不换玩法） | 3000 兵 `proc_ms` > 100（当前 352–411）；或单局 >200 单位时 <45fps | 单局 20~60 单位，**不需要** |
| B | **人群层接管"远景/大编队援军"**：超过 N 个单位的编队降级成人群实体 | 同屏战斗单位经常 **>200** | 20~60 → 差 3~10 倍 |
| C | **主战斗逻辑搬进 SoA**（丢举盾/逐单位动画/技能表现） | 同屏 **>800** 且 A/B 都到顶 | 远未到 |

一句话：**现在该做的是 A 的"卫生部分"（能拿 3~4×，不碰玩法），不是把人群层转正。**
VAT 只在这条链的 B/C 段有意义 —— 主线 60 个单位用节点 + 骨骼动画更便宜也更好看
（VAT 没有攻击前摇的逐单位差异、没有举盾、纹理还占 12MB/件）。
